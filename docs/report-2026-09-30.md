# usbPD — how the 9 V contract came about (2026-09-30)

**Result:** on an ESP32-C6 with a FUSB302, the firmware (written from scratch in one day) asks a 100 W
USB-PD charger for 9 V. The charger answers Accept and then PS_RDY, and the 9 V contract holds. It took
**~65 min of agent time without the board (10:38–11:42)** and **~25 min with it (20:05–20:30)**.
That is **46 commits** and about 4,700 lines (spec, knowledge, firmware, host sim).

For comparison: the Pi chain (mission-control, 188 attempts over several days) never decoded a
single PD message.

## Setup

- **Repo:** `~/dev/repos/usbPD`, new, with the firmware written from scratch. Only the rig (board, Mac
  USB cable, charger on a smart plug via `charger.sh`) and the spec texts were reused. The texts were
  the USB-PD R2.0/R3.2 full text and the FUSB302 datasheet.
- **Orchestrator:** Claude (main session). It plans, briefs the role agents, and passes results from
  one role to the next.
- **Four roles** (general-purpose subagents, rules in `AGENTS.md`):

| Role | Owns | May not |
|---|---|---|
| mr-knowitall | `docs/knowledge/`: facts with source refs | write firmware, touch the rig |
| mr-spec | `docs/spec.md`: state machine, transition table, tests | write firmware, touch the rig |
| mr-engineer | `fw/`, `test/host/`: table-driven state machine and host sim | flash, reset, serial port, charger |
| mr-bench | `bench/`, `runs/`: flash, reset, charger, capture, `bench/q` | change firmware logic |

- **Hard rules:**
  - Only mr-bench touches hardware.
  - The engineer sees board data only as filterable JSONL through `bench/q`.
  - Commit after every step.
- **Milestones:**
  - M0 Rig
  - M1 Knowledge
  - M2 Spec
  - M3 Host sim green
  - M4 First SRC_CAPS decoded
  - M5 5 V contract 2×
  - M6 Requested voltage (9 V)

Hands-on time with the board, from the first bench commit to the 9 V contract: **21 min**. There was
exactly one firmware bug on real hardware, and it was not a protocol error. The protocol logic worked
the first time the board got past the crash.

## Procedure: why it went fast

1. **Knowledge → spec → code, in strict order.** mr-knowitall collected cited facts first. The spec
   pinned down every transition before any firmware was written. The engineer asked questions
   formally (`docs/spec-questions.md`) instead of guessing.
2. **Table-driven state machine plus host sim.** The protocol logic was proven on the host
   (47 scenarios, fake FUSB302, fake source) before the board existed. On the board, only integration
   problems could remain, and only one did.
3. **Bench tooling built before it was needed.** Flash, capture, replug scenarios and `bench/q`
   were all self-tested against a fake board, so M0 was done in 5 minutes.
4. **Strict role separation with a data interface.** mr-bench does not fix firmware. It hands over
   evidence (run dir, decoded panics, exact queries). The engineer fixes without touching the board.
   Each handover was one report followed by one brief.
5. **Stop rule instead of grinding.** A failed milestone means at most ~3 runs, then a failure report.
   So the stack bug went bench → engineer → bench in 7 minutes.
6. **Instrumentation as part of the fix.** `hb.stack_free` shows the headroom directly: 6676 B at the
   lowest, measured through the whole 9 V sequence.

## Still open

- Q7, Q8, Q12, Q15: the hard/soft reset paths never triggered on the good path.
- After every contract, the charger sends 10× Discover Identity (VDM). The firmware ignores them, the
  charger gives up without a reset, and answering them properly would be cleaner.
- The step that takes caps and sends the Request needs 2.3–2.5 ms of poll time (target 2 ms). This is
  within spec, but it is the only `poll.slow`.
- A long 9 V soak, and 15 V / 20 V.
